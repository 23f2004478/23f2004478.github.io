Automated Finance Ledger Agent

Engineered an autonomous personal finance pipeline ingesting digital receipts from read-only Gmail to a self-hosted Firefly III ledger with deterministic idempotency and refund netting.

The Financial Data Ingestion Problem

Maintaining an accurate double-entry ledger of personal and business expenses usually fails for two distinct reasons:

  • Manual tracking friction: Entering receipts manually after each purchase leads to cognitive fatigue, missing transactions, and delayed reporting.
  • Aggregator surveillance and brittle connections: Commercial aggregators require direct banking credentials, sell aggregated user telemetry, and often fail on multi-item receipts, order cancellations, and refunds.
  • Unstructured confirmation formats: Transaction emails arrive across dozens of changing HTML layouts, plain text invoices, and PDF attachments requiring robust extraction that does not hallucinate numbers.

System Architecture

The system runs as an autonomous scheduled pipeline executing four deterministic stages from ingestion to ledger synchronization.

Text description of architecture: 1. Read-only Gmail API ingests digital receipt emails. 2. A dual-path parser processes known schemas with deterministic DOM extractors, using a constrained LLM fallback only for novel formats. 3. Normalization generates idempotent external IDs, nets refunds against parent categories, and standardizes to IST timestamps. 4. Verified transactions are posted to a self-hosted Firefly III double-entry ledger via REST API.

1. Ingestion via Read-Only Scopes

The pipeline accesses the mailbox strictly through a minimal read-only OAuth scope (gmail.readonly). It searches for transaction identifiers, order confirmations, and invoice attachments without permission to draft, send, or delete emails.

2. Dual-Path Parser & LLM Fallback Boundary

To ensure high throughput and zero hallucinated numbers, the extraction engine utilizes a two-tier approach:

  • Deterministic Tier (Primary): Known vendor layouts are parsed using explicit HTML DOM traversals and regex extractors. This processes structured transactions instantly with zero token expenditure.
  • LLM Fallback Tier (Secondary): When novel or irregular receipt emails fail pattern matching, an isolated model extracts the line items, taxes, discounts, and order numbers into a strict JSON schema with type validation.

3. Idempotency & Refund Netting Engine

Before submitting any transaction to the ledger, the data passes through a normalization layer:

  • Deterministic External IDs: Each transaction receives a unique hash generated from the merchant order identifier and transaction date. Re-running the ingestion job on overlapping time windows safely updates metadata without creating duplicate ledger rows.
  • Automated Refund Netting: Cancellation and refund emails are automatically identified and mapped back to the original purchase category, preserving accurate net expenditure reports.
  • Timezone Normalization: All purchase timestamps are standardized to Indian Standard Time (IST) to ensure consistency across international vendors.

4. Synchronization to Firefly III

Normalized payloads are dispatched to a self-hosted instance of Firefly III over a secure REST API. Transactions are categorized, tagged with order identifiers, and balanced across asset and expense accounts.

Security & Operational Governance

  • Read-only mailbox access: The application possesses zero email modification, deletion, or transmission capabilities.
  • Local credential vault: OAuth refresh tokens and API secrets reside in filesystem-restricted (0600) files on a private Linux VPS.
  • No financial figures in public artifacts: Operating in alignment with confidentiality rules, no spending numbers or merchant names are logged in public portfolios.
  • Self-hosted data sovereignty: All ledger databases and parsed records remain exclusively on private, encrypted self-hosted infrastructure.
