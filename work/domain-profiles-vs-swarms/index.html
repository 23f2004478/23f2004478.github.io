Why We Chose Domain Profiles Over Multi-Agent Swarms

A technical architecture review on agent topology, data boundaries, and token efficiency in a single-operator autonomous estate.

Architecture Decision
Domain Profiles + Ephemeral Roles (Two-Level Isolation)
Alternative Rejected
Standing Functional Multi-Agent Swarms (Shared Memory/State)
Core Constraints
Single-Writer Discipline · Physical Data Airgaps · Deterministic Pre-flight
Author & Date
Krishnendu Biswas · 6 Oct 2026

1. The Siren Song of Functional Multi-Agent Systems

When designing an autonomous agent platform to handle diverse operations, ranging from personal finance and academic research to commercial outreach and infrastructure engineering, functional decomposition is the standard intuitive proposal.

On a whiteboard, the design appears elegant:

  • A central orchestrator breaks down incoming goals.
  • Specialized standing agents handle specific functional jobs: a Researcher to gather information, an Analyst to test assumptions, a Writer to draft prose, and a Designer to format deliverables.
  • Dynamic coordination passes intermediate outputs across specialist hand-offs.

This design typically relies on two foundational assumptions: first, that smaller toolsets prevent hallucination; second, that specialized persona prompts produce superior domain expertise. However, when evaluated against production operations across 12 profiles and tens of millions of tokens, both assumptions fail under real-world operational constraints.

2. What Empirical Research and Industry Data Reveal

A. The Token Tax and Diminishing Returns

Anthropic Engineering's published research on their multi-agent research system (June 13, 2025) provides the clearest public benchmark on the economics of agentic parallelism. In their measurements, a single agent using tools consumes roughly 4x the tokens of a plain chat turn, while an orchestrator-worker multi-agent system consumes roughly 15x the tokens of a chat turn.

While Anthropic's supervisor system outperformed a single-agent baseline by 90.2% on open-ended research evaluations, their analysis revealed that three factors (token budget, tool call count, and model choice) accounted for 95% of performance variance. Token spend alone explained roughly 80% of the variance. In practice, the performance advantage of multi-agent orchestration is overwhelmingly driven by brute-force token consumption.

For routine operational, analytical, and systems engineering workflows, spawning standing functional agents burns massive compute budgets for marginal quality gains.

B. The Single-Writer Principle and Context Fragmentation

Cognition (the team behind Devin) identified a fundamental limitation in multi-agent collaboration: parallel writers introduce conflicting implicit decisions.

Context in an agent session is not merely the initial prompt; it encompasses the complete trace of file inspections, syntax probes, tool calls, and implicit architectural decisions. When multiple agents attempt to write to the same workspace or document simultaneously, these implicit decisions collide. Subagents lack the full historical arc of user intent, leading to fragmented naming conventions, conflicting dependencies, and duplicate logic.

Their core finding holds across production environments: multiple agents can be effectively utilized to read data, gather intelligence, explore search paths, or critique drafts, but write operations must remain strictly single-threaded.

C. Skill Selection versus Agent Proliferation

Recent empirical evaluations of tool-use architectures by Liu et al. (arXiv:2601.04748, January 2026, "When Single-Agent with Skills Replace Multi-Agent Systems and When They Fail") demonstrate that a single agent equipped with an organized tool library matches multi-agent accuracy across complex benchmarks.

Tool misselection in LLM agents does not scale linearly with the total number of available tools; rather, performance remains stable until a threshold where semantic overlap between similar tool descriptions causes confusion. The remedy for tool selection failure is structured tool categorization and curated prompt context, not spawning additional agents.

3. The Unspoken Challenge: Data Boundaries and Security Airgaps

In a production environment managing real-world personal, professional, and institutional operations, functional agent swarms create a critical security vulnerability: cross-domain data pollution.

In our operational estate, workloads belong to distinct domains:

  • Institutional and Academic Operations: Partner communications, institutional records, strict suppression lists, and non-negotiable data retention boundaries.
  • Personal Candidature: Individual resume tailoring, private interview preparation, and personal job trackers.
  • Personal Finance: Private ledger transactions, self-hosted financial databases, bank parsing secrets, and expense analytics.
  • Infrastructure and Host Operations: Systemd service units, reverse proxy configurations, and host secret engines.

If standing functional agents (such as a shared "Researcher" or "Slide Designer") were deployed across these tasks, their persistent memory stores, context caches, and session logs would inevitably cross-contaminate confidential institutional data with personal records. Prompt-level instructions are insufficient to enforce security boundaries.

Physical partition by domain (separate profiles with dedicated storage directories, independent state databases, isolated persistent memory ledgers, and distinct secret scopes) provides deterministic, zero-leak data boundaries.

4. Our Architecture: Domain Profiles + Ephemeral Functional Roles

Instead of standing functional agents or an unconstrained swarm, we adopted a two-level, data-isolated architecture:

  • Level 0: Hub (Default Profile): Acts as the primary interface and orchestrator, routing domain-specific tasks to domain owners exclusively through structured Kanban cards.
  • Level 1: Domain Owners: Long-lived profiles (such as Workhorse for commercial delivery, Academics for research, Personal Finance, and Infrastructure) with physical data isolation, dedicated workspaces, separate state databases, and sole-writer authority over disk artifacts.
  • Level 2: Ephemeral Subagent Roles: Short-lived subagents spawned on demand via delegate_task within the domain owner's session. They perform read-heavy tasks, such as parallel fact harvesting or adversarial critique, and terminate immediately upon returning structured findings.

Core Architectural Principles

  1. Life-Domain Isolation First: Profiles exist to enforce strict data perimeters and manage distinct cron schedules, not to simulate personality archetypes.
  2. Ephemeral Functional Roles: Specialized capabilities are invoked as short-lived subagent roles within the owning profile's session. They inherit the profile's security perimeter and vanish upon task completion.
  3. Strict Single-Writer Rule: The domain owner remains the primary author and sole disk writer. Helper roles harvest facts or produce defect lists; parallel disk writes are prohibited.
  4. Deterministic Pre-flight Before LLM: Code execution, exact string matching, SQL queries, and local Python checkers run before invoking high-tier reasoning models.

5. Pilot Instrumentation and Empirical Validation

To evaluate this architecture against monolithic baselines, we established an empirical validation framework tracking telemetry across active workloads:

  • Token Efficiency: Total token spend per finished deliverable (prompt tokens, completion tokens, and cache hit ratios).
  • Execution Latency: Wall-clock execution time and retry loops.
  • Quality Metrics: Defect fix rates within 7 days, reviewer change requests, and first-pass validation rates.

Explicit Kill Criteria

We will revert to monolithic single-session execution if:

  1. Token consumption exceeds 3x baseline without measurable quality improvements.
  2. Subagent crash rates exceed baseline worker errors.
  3. First-pass verification rates drop below baseline.
  4. Any cross-domain data leakage is detected.

By grounding our agent topology in physical data isolation, single-writer discipline, and empirical verification, we keep the estate fast, private, and dependable.
