Memory and self-documentation: five layers, capped notes and a lossless context engine

How 11 agents on one Azure server remember what matters. Small curated files hold what must survive, and LCM-X, a SQLite context engine, keeps every original message so a summary can always be checked against its source.

Built on Hermes Agent (open source, Nous Research) with the LCM-X context plugin. Private system; architecture and figures probed from the live host on 7 Oct 2026.

Problem: remembering everything makes agents worse

Agents that try to remember everything fail in two quiet ways. The context window fills with stale detail, so the model spends attention on noise. And a store full of unchecked fragments lets the model recall things that were never true. Neither failure raises an error.

Cutting old messages is not the answer either: the agent forgets earlier decisions, and a retried task starts from nothing. I wanted durable memory small enough to read in full, every durable write reversible, and the bulk of history compressed for the model without being thrown away.

Architecture: five layers, one job each

Each layer has one job, one rule for how long it lives, one size limit and one gate on who may write to it. The model reads only L1 directly. Everything else arrives through the context assembler or a tool call.

  • L1 Session window and system prompt: The system prompt, the agent's own rules file, the conversation and tool results. When it grows past the compaction threshold, LCM-X folds the oldest turns into summary nodes and keeps pointers to the originals.
  • L2 Ephemeral scratch: Each agent's TMPDIR points to its own cache/scratch directory. Downloads, extracted archives and probe scripts land there. Nothing in it is read by a later session, and entries idle for 24 hours are pruned.
  • L3 Curated persistent memory: Two markdown files per agent, MEMORY.md for notes and USER.md for the user profile, with hard character caps (2,200 and 2,600 on the router agent). Both are loaded in full in every session, so there is no ranking step and nothing to miss. The cap is the point: it forces curation.
  • L4 Curated knowledge base: 15 markdown files in ~/.hermes/knowledge, one topic each, plus an index. Facts about me and the system, written by hand and read on demand, so an agent loads only what its domain needs. A guardrails file records what is true in production and what was only prototyped.
  • L5 Procedural skills library: 310 SKILL.md files (203 distinct skills) across the router and 10 domain agents. Each skill says when to use it, the steps and the exit check, with references and runnable scripts beside it. Skills are procedures, not facts, so they live apart from L4.

Curation and rollback

Writes to L3 never go straight to disk. They pass a queue, a review and a snapshot first, so a bad fact can be undone.

  1. Queue: A memory write that needs approval is saved as a JSON record in ~/.hermes/pending/memory instead of being applied.
  2. Pre-filter: fable_memory_curator.py runs a cheap gate first that drops transient items before any expensive review.
  3. Review: Fable, the top reasoning tier, sorts each candidate. Durable rules and preferences are applied. Routine status is logged only, since LCM-X already holds the transcript. Anything about deletes, security or do-not-contact rules waits for me. Low-signal items are declined.
  4. Snapshot: Before applying anything, the curator copies MEMORY.md and USER.md to timestamped files in memories/backups (3 snapshots on disk today).
  5. Apply: Approved items go through the same path as a manual approval: file lock, drift guard and the character cap. The memory tool refuses a write that would pass the cap and asks for a merge. The file is written to a temp file, synced and renamed, so a reader never sees half a file.
  6. Ledger and rollback: An hourly job syncs memory_ledger.py, a SQLite ledger that records where each remembered claim came from and what replaced it. Rollback restores a snapshot. A forget leaves a tombstone, and an explicit purge redacts the source rows after a backup.

A separate hourly job backs up agent state and memory, and md_guard.py runs daily to catch knowledge edits that drift into the wrong file.

LCM-X: lossless context memory

LCM-X sits beneath L1. Every message is written once to lcm.db and gets a permanent store_id. When the window needs room, LCM-X compacts a run of messages into a depth 0 summary node that lists the store_ids it covers. When depth 0 nodes pile up, they compact into a depth 1 node that lists their node_ids. The result is a directed graph in which summaries point down to summaries or raw rows, and compaction never rewrites a raw row.

  • Compaction: The router agent's store holds 196,309 messages from 149 sessions and 41 summary nodes, 39 at depth 0, 2 at depth 1. Deepest level in use: 1.
  • Retrieval: SQLite FTS5 indexes both messages and summary nodes. Search ranks by match strength weighted by recency, so exact names, file paths and ids are found directly. The plugin also has an embedding path and rank fusion, but both are switched off in production, so retrieval today is keyword based.
  • Expansion: If a summary is not enough, lcm_expand returns the original messages by node_id or store_id. Compaction loses detail in the window, never in the store.
  • Concurrency: WAL mode lets readers proceed while a compaction writes, so one agent can read history while another session compacts.

Integrity check behind the lossless claim: every id listed by any summary node must exist. Result on 7 Oct 2026: 0 dangling references out of 3,164.

SELECT COUNT(*) FROM summary_nodes s, json_each(s.source_ids) j
WHERE (s.source_type = 'messages'
       AND NOT EXISTS (SELECT 1 FROM messages m WHERE m.store_id = j.value))
   OR (s.source_type <> 'messages'
       AND NOT EXISTS (SELECT 1 FROM summary_nodes n WHERE n.node_id = j.value));

Prototype and production

What ran where

From 11 to 20 Sep 2026 the agents ran in a Linux VM on my MacBook, and memory was prototyped there with local vector embeddings and the Hindsight memory API. On 20 Sep 2026 the runtime moved to the Azure server. Hindsight was replaced by native memory and skills, and neither the local embeddings nor Hindsight was deployed to the server. Production memory is the five layers above plus LCM-X on SQLite.

Design decisions

  • Hard caps on L3, not soft warnings: Soft limits get ignored under pressure. A hard cap forces the merge now.
  • Markdown for L3 and L4, not a key-value store: Readable, diffable and editable in any editor, because I am the final curator.
  • SQLite WAL for history, not a JSONL log: Concurrent readers, transactional compaction and FTS5 in one file.
  • Keyword search first: The most common lookups are names, paths and ids, which exact matching finds outright. The embedding path stays off until it earns its cost.
  • Keep the originals: A summary is a guess about what mattered. The original is the evidence.
